# industry-research-draft-workflow 统一设计

## 设计目标

`industry-research-draft-workflow` 是面向行业研究工作的底稿工作流 skill。它不再只是“Excel 图表格式适配器”，而是指导 agent 判断场景、组织材料、规划数据采集顺序、生成或改造可复核的 Excel 研究底稿，并在 PPT 修改、表述核验、数据收集等高频场景中保证来源证据可追溯。

仓库项目目录暂保留 `draft-excel-format-adapter/` 作为历史开发目录；真正的 skill 安装名、frontmatter name 和打包名称统一为 `industry-research-draft-workflow`。

## 边界定义

### 本 skill 负责

- 判断用户请求属于哪类底稿场景。
- 指导 agent 按正确顺序收集材料、数据、截图和来源说明。
- 将现有文件改造为底稿模板或模板参考。
- 为数据收集、表述核验、材料整理等通用行研场景生成底稿。
- 在通用数据采集场景中指导数据源优先级、采集顺序、证据记录和底稿化写法，覆盖公司官网、微信公众号、公司公告、rankings/榜单等来源。
- 为复杂具体场景提供底稿规范入口、注册表和交接接口，例如 PPT 修改同步底稿。
- 定义 Excel 底稿的工作簿结构、证据底稿格式、质量门槛和验证项。
- 提供少量确定性脚本，用于扫描、脚手架、校验、打包和资产补齐。

### 本 skill 不负责

- 不实现 rankings 数据源抓取器、标准化器、数据库快照或榜单适配器。
- 不替代 `ranking-skill` / rankings 项目中的采集、清洗、历史维护和展示层逻辑。
- 不替代公司官网、微信公众号、公告平台、金融终端等专用采集 skill 或外部系统；只规定底稿所需的数据采集顺序、来源记录和证据要求。
- 不承载复杂具体场景的完整执行流程，例如 PPT 修改、PPT 生成、图表重建、数据库抓取或 rankings 适配。
- 不替代未来独立的复杂场景 skill；只提供底稿相关规范和注册入口。
- 不把单个公司、单次任务、一次性路径或具体数据写入通用 skill 规范。

## 设计原则

1. **场景路由优先**：`SKILL.md` 应先判断任务类型，再指向对应 reference。
2. **渐进式加载**：`SKILL.md` 是目录和决策树，细节放到一层 `references/` 文件中，避免把所有规则堆进主文件。
3. **确定性脚本只做稳定动作**：脚本用于扫描、生成骨架、验证和打包；业务判断留给 reference 和 agent 推理。
4. **底稿证据链统一**：所有场景最终都要回答“这条表述/数据从哪里来，截图或原始文件在哪里，口径是否清楚”。
5. **最小改造优先**：已有正式底稿、PPT、项目包默认保留结构；除非用户明确要求，不重建交付物。
6. **项目产物与通用流程分离**：任务产物留在项目包，可复用流程再沉淀到 skill。
7. **复杂场景可注册**：复杂场景只在本 skill 中登记底稿接口和质量要求，完整流程应沉淀到独立 skill。

## 核心场景设计

### 场景 A：现有文件改造为底稿模板

触发语义：

- “把这个文件改造成底稿模板”
- “从这个 Excel/PPT/底稿里沉淀模板”
- “按这个格式以后复用”
- “把现有底稿整理成模板”

流程：

1. 扫描输入文件：Excel、PPT、截图、PDF、已有底稿。
2. 识别可复用元素：sheet 结构、图表样式、证据表布局、批注规则、命名规则、来源字段。
3. 区分“模板契约”和“一次性任务数据”。
4. 生成模板说明或模板副本。
5. 保留原始文件，不覆盖正式交付物。
6. 输出模板使用说明和待补充项。

关键产物：

- 模板 workbook 或模板说明。
- 模板字段契约。
- 样式/图表提取记录。
- 不应纳入模板的一次性内容清单。

### 场景 B：通用行研底稿生成

触发语义：

- “把数据收集写成底稿”
- “把这些材料整理成底稿”
- “做一个表述核验底稿”
- “为这个研究问题生成底稿”
- “收集某行业/公司/产品数据并做证据底稿”

推荐 workbook 结构：

```text
数据总表
主题分表（可选）
证据底稿
待核验
说明（可选）
```

通用流程：

1. 明确研究问题、审阅对象、数据截止期和输出范围。
2. 建立采集任务清单。
3. 按来源优先级收集材料和数据。
4. 将数据结构化到 `数据总表` 或主题分表。
5. 将关键表述、数字和判断写入 `证据底稿`。
6. 为每条关键内容配对来源截图、原始文件路径、链接、页码或抓取时间。
7. 对口径不清、来源不足、页面不可访问、估算类数据写入 `待核验`。
8. 做截图视觉校验和 workbook 可打开校验。
9. 最终输出中文文件名、中文 sheet 名、中文表头和中文说明。

### 场景 C：数据采集指引

该场景从“rankings / 榜单类数据的底稿采集指引”升级为通用数据采集指引。它服务于场景 B 的底稿生成，也服务于场景 A/E/D 中需要补充来源证据的任务。

本 skill 只指导 agent 如何选择数据源、按什么顺序采集、如何记录来源证据、如何把结果写入底稿。具体采集器、平台登录、API 抓取、数据库快照、rankings 适配、微信公众号 RSS/接口、公告平台解析等执行逻辑，应交给对应专用 skill 或项目维护。

#### 通用采集顺序

1. **项目内已有材料和历史产物**
   - 当前项目包 `01_材料收集` 或 `01_材料`
   - 历史底稿、历史 PPT、历史文字稿
   - 已有截图、PDF、Excel、CSV、Markdown 采集记录
   - `output/spreadsheet/`
   - `output/*.csv`
   - 采集记录、材料清单、数据源清单

2. **公司和主体官方来源**
   - 公司官网、投资者关系页面、新闻稿、产品页
   - 公司公告、年报、季报、招股书、业绩演示材料
   - 交易所/公告平台，例如 CNINFO、港交所披露易、SEC EDGAR 等
   - 官方博客、官方文档、官方 GitHub 或开发者页面
   - 官方微信公众号、视频号、微博、LinkedIn、X 等官方账号

3. **行业和平台型一手来源**
   - rankings/榜单官方网站
   - benchmark 官网或公开结果页
   - 页面内嵌 JSON / script payload
   - 官方 API、CSV、JSON、下载文件
   - 金融终端导出表和终端截图
   - 行业协会、政府数据库、监管数据库

4. **可信二级来源**
   - 券商研报、行业报告、咨询报告
   - 可追溯媒体报道
   - 数据服务商页面
   - 第三方估算或整理表

5. **待核验来源**
   - 口径不清的第三方估算
   - 无法访问的动态页面
   - 只有截图没有链接或文件名的材料
   - 缺少时间点的数据
   - 与历史数据冲突的指标

#### 常见来源类型规范

##### 公司官网

优先采集：

- 投资者关系页面。
- 新闻稿或公告页面。
- 产品介绍页。
- 财报/演示材料下载页。

记录：

- 页面标题。
- URL。
- 访问日期。
- 支撑表述的截图。
- 如为下载文件，保存文件名、发布日期、页码。

##### 微信公众号

优先采集：

- 公司官方公众号原文。
- 已接入的 WeChat/RSS/WeWe RSS 导出。
- 用户提供的文章链接、截图或导出文件。

记录：

- 公众号名称。
- 文章标题。
- 发布时间。
- 原文链接或导出文件路径。
- 支撑表述的截图。
- 若来自 RSS 或中间服务，记录服务名称和抓取时间。

限制：

- 如果公众号页面需要登录、反爬或只能通过截图访问，应在 `待核验` 中标记。
- 不把没有来源标识的截图当作强证据。

##### 公司公告

优先采集：

- 交易所或法定披露平台原文。
- 公司 IR 页面同步文件。
- 已下载 PDF 或公告 HTML。

记录：

- 公告标题。
- 公告日期。
- 披露平台。
- 证券代码或主体名称。
- 文件路径或 URL。
- 页码和截图。

##### rankings / 榜单类数据

该类来源仍放在数据采集指引内，不单独设 `rankings-source-adapter.md`。具体 rankings 抓取、标准化、历史快照和展示逻辑移交给 rankings 项目维护。

推荐优先查：

1. 项目内已有 rankings 成果：
   - `ranking-skill/`
   - `openrouter-rankings/`
   - `llm-stats-rankings/`
   - `artificialanalysis-rankings/`
   - 历史 workbook、CSV、SQLite snapshot、cached HTML

2. 原始数据源：
   - 官方 rankings 页面
   - 页面内嵌 JSON / script payload
   - 官方 API
   - 官方导出 CSV / JSON
   - 已缓存 HTML 或历史 raw response

每条 rankings 数据至少记录：

- 榜单名称
- 指标口径
- 排名或数值
- 主体名称
- 数据时间点
- 来源 URL 或本地文件
- 抓取/访问时间
- 来源类型：官方、第三方、估算、缓存、历史输出
- 证据截图、缓存文件路径或原始导出文件
- 待核验说明（如有）

#### 底稿写法

- 结构化数据进入 `数据总表` 或主题分表。
- 原始来源、截图、缓存说明进入 `证据底稿`。
- 口径不清、动态加载失败、历史值缺失、估算冲突、来源不可访问进入 `待核验`。
- 若某数据源需要长期维护，应转交对应专用 skill 或项目，而不是在本 skill 中新建采集适配器。

### 场景 D：复杂具体场景注册入口

该场景不是一个固定的 PPT 内置流程，而是一套可拓展的复杂场景接入机制。`industry-research-draft-workflow` 只维护这些复杂场景中“底稿相关”的规范、字段、质量门槛和转交入口。复杂场景的完整执行流程应放到独立 skill 或项目 workflow 中。

触发语义：

- “这个复杂场景需要底稿规范”
- “为某个专项 workflow 注册底稿要求”
- “PPT 修改同步底稿”
- “某个独立 skill 需要读取底稿规范”
- “把这个场景接入行业研究底稿工作流”

设计目标：

1. 让 A/B/E 继续作为本 skill 的核心能力。
2. 让复杂场景能以 registry 的方式加入，而不是把全流程塞进本 skill。
3. 让未来独立 skill 可以读取这里的底稿契约，知道应该产出哪些底稿字段、证据和校验结果。
4. 让本 skill 能在识别复杂任务时，把用户引导到对应场景 skill，同时保留底稿规范入口。

#### 复杂场景注册字段

每个复杂场景在 `complex-scenario-registry.md` 中至少记录：

- `scenario_id`：稳定英文 ID，例如 `ppt-modification-draft-sync`。
- `display_name`：中文场景名。
- `trigger_phrases`：典型触发语义。
- `owning_skill`：负责完整流程的独立 skill 名；若尚未创建，标记为 `planned`。
- `draft_role`：底稿在该场景中的职责。
- `required_draft_sections`：该场景至少需要哪些 sheet 或字段。
- `evidence_requirements`：来源、截图、原始文件、页码、缓存等要求。
- `handoff_contract`：本 skill 与独立场景 skill 的交接输入/输出。
- `quality_gates`：该场景除通用质量门槛外的额外检查项。
- `out_of_scope`：明确不由本 skill 执行的部分。

#### 复杂场景处理流程

1. 识别用户请求是否属于已注册复杂场景。
2. 如果存在 `owning_skill`，优先建议或调用该 skill 执行完整场景流程。
3. 本 skill 只加载通用底稿契约和该场景的底稿字段要求。
4. 输出或校验底稿相关部分：sheet、字段、证据、截图、待核验、一致性检查。
5. 不在本 skill 中实现该复杂场景的业务全流程。

#### 注册样例：PPT 修改同步底稿

`scenario_id`: `ppt-modification-draft-sync`

`display_name`: PPT 修改同步底稿

`owning_skill`: `planned:ppt-modification-draft-sync`

触发语义：

- “按材料改 PPT 并补底稿”
- “PPT 修改需要同步底稿”
- “生成 PPT 修改对应的底稿”
- “更新路演材料并保留来源”

本 skill 只负责该场景中的底稿规范：

- 每个 PPT 更新点应在底稿中有一行或一个证据块。
- 底稿记录页码、更新对象、原表述/原数据、新表述/新数据、更新原因、来源文件/链接/页码、证据截图、PPT 截图、核验状态。
- 底稿应能支持 PPT 修改后复核：为什么改、改成什么、依据在哪里、截图在哪里。
- 若涉及项目包，应对齐 `E:\Project\实习\底稿相关工作流` 的目录约定，但本 skill 不执行 PPT 修改全流程。

完整 PPT 修改流程不放在本 skill 中。未来创建独立 skill 时，该 skill 应负责：

- 解析 PPT 修改需求。
- 管理 PPT 文字稿。
- 修改 PPT。
- 导出 PPT 截图或 montage。
- 将更新点交给本 skill 的底稿规范生成或校验底稿。

底稿推荐字段：

- PPT 页码
- 更新对象
- 原表述/原数据
- 新表述/新数据
- 更新原因
- 来源文件/链接/页码
- 证据截图
- PPT 截图
- 核验状态

`out_of_scope`：

- PPT 文件编辑。
- 幻灯片渲染。
- 图表重建。
- 完整项目包执行流程。
- 公司或单次任务数据沉淀。

### 场景 E：已有底稿最小更新 / 图表模板适配

保留当前版本的成功经验：

- 已有 workbook 默认最小更新。
- 保留 sheet 顺序、公式、截图、来源备注和审阅结构。
- 图表模板适配独立于表格布局。
- 先生成 preview copy，再覆盖正式文件。

该场景继续由 `current-project-pattern.md` 和 `inspect_draft_excel_style.py` 支撑。

## 脚本设计

### 已有脚本

- `ensure_draft_excel_skill_assets.py`：检查和恢复缺失 skill 资产。
- `inspect_draft_excel_style.py`：检查 workbook sheet、图表颜色、样式和字体信号。

### 建议新增脚本

#### profile_input_assets.py

用途：扫描用户给定目录或文件，生成场景判断线索。

输出：

- 发现的 Excel/PPT/PDF/图片/CSV/Markdown 文件。
- 可能的当前底稿、原始材料、来源截图、脚本、最终交付物。
- 建议场景：模板改造、底稿生成、PPT 同步、已有底稿更新。

#### scaffold_draft_project.py

用途：按项目包规范创建底稿工作区或项目包骨架。

输出：

```text
00_项目说明.md
01_材料收集/
02_PPT文字稿/
03_PPT修改/
04_底稿修改/
05_脚本/
06_截图预览/
99_历史版本/
```

#### build_evidence_workbook.py

用途：从 CSV/JSON/Markdown manifest 生成基础证据底稿 workbook。

输入字段可包括：

- 内容
- 来源 URL
- 来源文件
- 页码
- 截图路径
- 备注

#### validate_evidence_workbook.py

用途：检查 workbook 是否满足质量门槛。

检查项：

- workbook 可打开。
- 关键 sheet 存在。
- `证据底稿` 有 `内容` 和 `来源/备注`。
- 截图文件路径存在或批注可追溯。
- `待核验` 项不为空时有说明。
- 表头和关键说明为中文。

## 质量门槛

所有场景交付前至少确认：

- 原始材料保留且不覆盖。
- 数据来源已登记或可追溯。
- 关键表述和数据有证据截图或原始文件支撑。
- 证据和结论没有错位。
- 动态页面、反爬、空白页、付费墙、估算值已标记。
- 中文命名和中文表头符合交付习惯。
- Excel 可打开。
- 如涉及 PPT，PPT 可打开且可导出截图。
- PPT、文字稿、底稿的数字和口径一致。

## 评测用例

下一版至少准备 4 类 eval：

1. **现有 Excel 改造成底稿模板**
   - 输入：一个已有底稿 workbook。
   - 期望：输出模板化步骤、保留/剥离内容清单、模板契约。

2. **数据收集生成底稿**
   - 输入：若干数据项、链接和截图。
   - 期望：生成包含 `数据总表`、`证据底稿`、`待核验` 的 workbook 方案或文件。

3. **数据采集指引**
   - 输入：用户要求收集公司官网、微信公众号、公告或模型排名数据。
   - 期望：按项目内已有材料、官方来源、平台型一手来源、可信二级来源、待核验来源的顺序指导采集；输出底稿证据字段；不生成任何专用采集适配器。

4. **复杂场景注册：PPT 修改同步底稿**
   - 输入：PPT、材料、更新说明。
   - 期望：识别为复杂注册场景；只输出底稿字段、证据要求、交接契约和质量门槛；不执行或描述完整 PPT 修改流程。
